# Milestone 6 verification

What was checked on the milestone 6 build on `main` (with the remote protocols wired into the app, cross-provider copy and move, resumable transfers and remote thumbnails, #487 to #489, #498, #499 and #508, all merged), how, what was found, and what is still open. The headless suites and the real-server integration tests cover the providers; this records a first pass through the running app against real servers, on one Linux desktop. It says what was run and what was not; nothing here is claimed from reading the code.

Status: a first Linux pass on a headless GNOME compositor, with the gaps in §5 · KDE Plasma, Cinnamon, the Flatpak portal route and Windows 11 not run · #309

## 1. How it was run

| Pass       | Where                                                                                                              | How                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux live | `mutter --headless --wayland --no-x11` (1400 × 900 virtual monitor), WebKitGTK, `WEBKIT_DISABLE_DMABUF_RENDERER=1` | `bun run tauri:dev` (a debug build) driven over the Tauri MCP bridge in a private `dbus-run-session` with `xdg-desktop-portal`, a private `gnome-keyring-daemon --unlock --components=secrets` and a private `ssh-agent`; private `HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `XDG_RUNTIME_DIR`, so the real settings, keyring and `~/.ssh/known_hosts` were never touched |
| SFTP       | OpenSSH `sshd -D -f <config>` as the current user on port 2232, ed25519 host and client keys                       | The client key in the private agent ("Automatically"); a second host key for the changed-key check; a Python TCP proxy adding 50 ms each way (100 ms round trip) on port 2233                                                                                                                                                                                                                   |
| SMB        | Samba `smbd -F --no-process-group` with a private state directory on port 4455                                     | A `tdbsam` account added with `pdbedit`, password login                                                                                                                                                                                                                                                                                                                                         |
| WebDAV     | `rclone serve webdav` on port 8089                                                                                 | Basic authentication                                                                                                                                                                                                                                                                                                                                                                            |
| S3         | `rclone serve s3` on port 8090                                                                                     | An access key pair, the MinIO preset (path-style)                                                                                                                                                                                                                                                                                                                                               |
| Fixtures   | `~/.cache/waypoint-verify` on the NVMe disk, deleted afterwards                                                    | One folder served by all four servers: 10,000 and 100,000 empty files, odd names (spaces, `#`, `%`, `%25`, non-ASCII, a 240-character name, a name that is not UTF-8), a 2 GiB sparse file, a 64 MiB random file, a symlink, a file with mode `000`; `zip`, `tar.gz`, `7z`, a nested zip, an encrypted zip and a zip of 20,000 entries; a Git repository with every status                      |

The host is the one in `milestone-5-verification.md` §1 (Ryzen 7 7700X, 30 GB, Linux 7.1.9, btrfs on NVMe). All servers ran on loopback, so "LAN" below means loopback. The app was a debug build, and every timing is from the page (`performance.now()` from the double-click to the status bar's count and to the first painted row name), so it includes the bridge and the render.

## 2. Performance against the remote listing budget

The budget is the one in `remote-locations.md` (spike #278): first rows within three round trips plus 50 ms; 100,000 entries in 0.5 s on a LAN, 1 s at 10 ms and 5 s at 100 ms. It was written from SFTP; it is applied to the others for comparison.

| Protocol and link       | 10,000 entries: first batch / all counted / rows painted | 100,000 entries: first batch / all counted / rows painted                          | Verdict                                                                                      |
| ----------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| SFTP, LAN (5 runs)      | 27 to 39 ms / 49 to 53 ms / 57 to 65 ms                  | 26 to 39 ms / 346 to 351 ms / 355 to 362 ms (3 runs)                               | total **met** (0.36 s against 0.5 s)                                                         |
| SFTP, 100 ms round trip | 320 ms / 531 ms / 660 ms                                 | 320 ms / 1,979 ms / 2,132 ms                                                       | total **met** (2.1 s against 5 s); first rows **not met**: placeholders until the end (#511) |
| SMB, LAN                | — / 240 to 245 ms / 254 to 260 ms                        | 2,754 ms / 2,800 ms / 2,813 ms                                                     | **not met** (2.8 s; `smbclient` lists the same folder in 1.09 s) (#512)                      |
| WebDAV, LAN             | 132 ms / 351 ms / 361 ms                                 | — / 6,964 ms / 7,014 ms                                                            | **not met** (7.0 s; the server answers the `PROPFIND` in 1.03 s) (#512)                      |
| S3 (`rclone`), LAN      | 120 ms / 616 ms / 629 ms                                 | not run (`rclone serve s3` re-reads the folder for every page, as the spike found) | recorded; the provider's own 100,000-key figure is in SPEC (0.36 s in memory)                |

In every protocol the status bar counts the batches as they arrive ("Scanning… 20,098 items found so far"), but the rows stay grey placeholders until the listing is complete, so "first rows visible" is the total time (#511). Over the 100,000-entry SFTP folder, sorting by name descending took 77 ms, scrolling 600 px a frame for 120 frames gave frames of p50 9 ms, p95 15 ms, worst 26 ms with no blank rows afterwards, and a three-row Shift selection showed "3 items selected" in the Inspector and the status bar.

Not measured: the 10 ms link, process memory over idle for 100,000 entries, and transfer throughput beyond the one copy below (39 MB/s SMB to WebDAV, shown by the Operations popover).
