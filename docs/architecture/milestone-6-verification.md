# Milestone 6 verification

What was checked on the milestone 6 build on `main` (with the remote protocols wired into the app, cross-provider copy and move, resumable transfers and remote thumbnails, #487 to #489, #498, #499 and #508, all merged), how, what was found, and what is still open. The headless suites and the real-server integration tests cover the providers; this records a first pass through the running app against real servers, on one Linux desktop. It says what was run and what was not; nothing here is claimed from reading the code.

Status: two Linux passes on a headless GNOME compositor (the second in §6), with the gaps in §5 and §6.5 · KDE Plasma, Cinnamon, the Flatpak portal route and Windows 11 not run · #309

## 2. Performance against the remote listing budget

The budget is the one in `remote-locations.md` (spike #278): first rows within three round trips plus 50 ms; 100,000 entries in 0.5 s on a LAN, 1 s at 10 ms and 5 s at 100 ms. It was written from SFTP; it is applied to the others for comparison.

| Protocol and link       | 10,000 entries: first batch / all counted / rows painted | 100,000 entries: first batch / all counted / rows painted                          | Verdict                                                                                      |
| ----------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| SFTP, LAN (5 runs)      | 27 to 39 ms / 49 to 53 ms / 57 to 65 ms                  | 26 to 39 ms / 346 to 351 ms / 355 to 362 ms (3 runs)                               | total **met** (0.36 s against 0.5 s)                                                         |
| SFTP, 100 ms round trip | 320 ms / 531 ms / 660 ms                                 | 320 ms / 1,979 ms / 2,132 ms                                                       | total **met** (2.1 s against 5 s); first rows **not met**: placeholders until the end (#511) |
| SMB, LAN                | — / 240 to 245 ms / 254 to 260 ms                        | 2,754 ms / 2,800 ms / 2,813 ms                                                     | **not met** (2.8 s; `smbclient` lists the same folder in 1.09 s) (#512)                      |
| WebDAV, LAN             | 132 ms / 351 ms / 361 ms                                 | — / 6,964 ms / 7,014 ms                                                            | **not met** (7.0 s; the server answers the `PROPFIND` in 1.03 s) (#512)                      |
| S3 (`rclone`), LAN      | 120 ms / 616 ms / 629 ms                                 | not run (`rclone serve s3` re-reads the folder for every page, as the spike found) | recorded; the provider's own 100,000-key figure is in SPEC (0.36 s in memory)                |

In every protocol the status bar counts the batches as they arrive ("Scanning… 20,098 items found so far"), but the rows stay grey placeholders until the listing is complete, so "first rows visible" is the total time (#511). Over the 100,000-entry SFTP folder, sorting by name descending took 77 ms, scrolling 600 px a frame for 120 frames gave frames of p50 9 ms, p95 15 ms, worst 26 ms with no blank rows afterwards, and a three-row Shift selection showed "3 items selected" in the Inspector and the status bar.

Not measured: the 10 ms link, process memory over idle for 100,000 entries, and transfer throughput beyond the one copy below (39 MB/s SMB to WebDAV, shown by the Operations popover).

## 6. Second pass

A second pass ran what the first did not, on `main` with every milestone 6 change merged (transfers with resume and remote thumbnails, writable archives, the listing fixes #521 and #522, the small fixes #517 to #519, the Experimental switches and the S3 wiring). As before, it says what was run and what was not; nothing here is claimed from reading the code.

### 6.1 How it was run

The setup of §1, rebuilt: the same private session (`dbus-run-session`, headless mutter at 1400 × 900, a private keyring, `xdg-desktop-portal` and `ssh-agent`, private `HOME` and `XDG_*` directories), user-level `sshd` on port 2232, Samba on 4455, `rclone serve webdav` on 8089 and `rclone serve s3` on 8090, and fixtures under `~/.cache/waypoint-verify` (a 400 MiB and a 64 MiB random file, twelve small PNG images and a 6 MiB JPEG with an EXIF thumbnail, 100,000 empty files, zip, tar.gz, 7z, an encrypted zip, a zip of 20,020 entries, a zip with `../` and `/` names, and a Git repository on a branch with a modified and an untracked file), all deleted afterwards. A Python TCP proxy sat in front of SFTP (port 2233, 50 ms each way) and SMB (port 4456, no delay); a lost connection is that proxy being killed and started again.

Two things differ from the first pass:

- **Real keyboard input.** The bridge's key events are synthetic, so Tab does not move focus and Enter does not press a button. Keys were sent instead through mutter's own `org.gnome.Mutter.RemoteDesktop` D-Bus API (`NotifyKeyboardKeysym` in a remote-desktop session on the private bus), which the page receives as trusted events. The keyboard results below come from that; focus order was read from `focusin` events.
- **The accessibility snapshot works** in the main window this time (roles, names, states and descriptions of the Connect dialog, the Operations popover and the archive dialogs came from it). In the Settings window it still fails with "aria-api library not loaded", so the Settings checks are from the DOM and screenshots.

The private `XDG_DATA_HOME` is on tmpfs while the fixtures are on `/home`, so the Trash for them would be `/home/.Trash-1000`, which cannot be made; every Move to Trash there failed ("The Trash is not available: cannot create /home/.Trash-1000: Permission denied"). That is this setup, not the app, but it decided what could be checked of archive Undo (§6.3). The web process of the main window died once after a restart for no reason found (no crash report, other agents' WebKit apps were running beside it, and memory was tight at 3 GB free); a fresh start did not repeat it.
