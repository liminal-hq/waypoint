# Architecture Decision Log

Product and design decisions are D-numbers in `../decisions.md`. Architecture decisions are A-numbers here. Status is **Proposed** until reviewed; change it to **Accepted** (with the date) or **Superseded by An** when decided. Milestone 0 spikes append their results here.

| #   | Status                | Decision                                                                                                                                                                                                                                                                                                                                                                                   | Reasoning                                                                                                                                                                                                                                                                                                    |
| --- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A1  | Proposed              | **Cargo workspace + Bun workspaces**, layout `apps/`, `packages/`, `crates/`, `plugins/`, `docs/`, `scripts/`.                                                                                                                                                                                                                                                                             | Matches Jar and Cadence (Bun) and Threshold and Spindle (Cargo workspace, plugins directory); Bun is the newest house choice.                                                                                                                                                                                |
| A2  | Proposed              | **React 19 + TypeScript strict + Vite** front end, virtualised lists, React Compiler; fallback is SolidJS for the file-view surface only, decided by spike 1.                                                                                                                                                                                                                              | Family reuse of the shared chrome and house patterns outweighs the modest performance edge of fine-grained frameworks once lists are virtualised and Rust owns the data. See `frontend.md`.                                                                                                                  |
| A3  | Proposed              | **Rust owns state; the front end renders.** One writer per piece of state, monotonic revisions, granular events, `Channel`s for streams, listing handles with range fetch.                                                                                                                                                                                                                 | Threshold event-hub and Jar sim-core patterns; keeps the JS heap small and multi-window state consistent. Handle-versus-push is confirmed by spike 1 and 5.                                                                                                                                                  |
| A4  | Proposed              | **Pure crates for logic, thin plugins for the Tauri surface.** Reusable plugins are self-contained and import nothing from Waypoint.                                                                                                                                                                                                                                                       | Jar's `jar-core` + `tauri-plugin-jar` split; makes logic testable headlessly and plugins publishable.                                                                                                                                                                                                        |
| A5  | Proposed              | **Incubate reusable plugins and `packages/chrome` in-repo; graduate to `tauri-plugins-workspace` (plugins) and a shared package (chrome) on a checklist.**                                                                                                                                                                                                                                 | Real consumer while the API is unsettled, then shared without churn. Resolves the mechanics of open question 2.                                                                                                                                                                                              |
| A6  | Proposed              | **Every plugin exposes `get_status`** (`available`, `reason`, features) and platform code lives in per-platform modules with an `unsupported` fallback.                                                                                                                                                                                                                                    | Implements the "hide what isn't available" principle and the Services panel; avoids scattered `#[cfg]`.                                                                                                                                                                                                      |
| A7  | Proposed              | **Extension runtime deferred to milestone 8.** Build the extension-point registry, manifest and permission model first, with bundled features as first-party extensions; then choose WASM (component model) versus JS.                                                                                                                                                                     | Open question 3; the registry and permissions are needed either way, and first-party use proves the API before a runtime is fixed.                                                                                                                                                                           |
| A8  | Proposed              | **CI/CD follows the house pipeline** (Jar reference): `ci.yml` gate, `publish-test-results.yml`, tag-driven `release.yml`, synchronised versions, `tauri-ci-desktop` container, `ts-rs` drift check, licence-header check, Dependabot grouping.                                                                                                                                            | Consistency across the org; `ci-cd.md`.                                                                                                                                                                                                                                                                      |
| A9  | Proposed              | **Directory listings are handles** (Rust-held sorted/filtered index, `get_range`, change events) rather than pushed arrays.                                                                                                                                                                                                                                                                | Scales to very large folders and keeps sort/filter logic in Rust; replaced by chunked push if spikes 1 and 5 show no benefit.                                                                                                                                                                                |
| A10 | Proposed              | **Own pointer-event drag engine in the front end; `native-dnd` plugin for OS-level in and out.**                                                                                                                                                                                                                                                                                           | Tauri's native drag-drop and HTML5 DnD conflict on some platforms and cannot start outbound drags; the required behaviours (spring-load, action picker, tear-off) are not stock DnD. Confirmed by spike 4.                                                                                                   |
| A11 | Proposed              | **Windows 11 modules are written with each Linux module** from milestone 2, with a `windows-check` CI job.                                                                                                                                                                                                                                                                                 | D46 makes Windows a real target; retrofitting per-platform modules later is costlier than writing them together.                                                                                                                                                                                             |
| A12 | Accepted (2026-09-29) | **Terminology:** "native plugin" = Tauri plugin; "extension" = user-installable sandboxed add-on (UI label "Plugins").                                                                                                                                                                                                                                                                     | Two meanings of "plugin" collide in this project; unqualified use is banned in code and PR titles.                                                                                                                                                                                                           |
| A13 | Proposed              | **Licence:** Apache-2.0 OR MIT, header on every source file, `scripts/check-headers.sh` in CI.                                                                                                                                                                                                                                                                                             | Matches Cadence, Jar and `tauri-plugins-workspace`; required for reusable plugins to graduate.                                                                                                                                                                                                               |
| A14 | Accepted (2026-09-29) | **Scaffold Milestone 1 now; run the Milestone 0 spikes alongside it.** Spike results are appended here, and A2, A3, A9 and A10 stay Proposed until they report.                                                                                                                                                                                                                            | Avoids blocking on throwaway experiments; what Milestone 1 creates (skeleton, protocol crate, chrome, CI) does not depend on the spike outcomes. Risk: some rework if a spike overturns A2 or A9, contained by keeping the file-view surface behind a narrow interface.                                      |
| A15 | Accepted (2026-09-30) | **`system-appearance` is the first reusable plugin, built in this repo to graduate to `tauri-plugins-workspace`.** It reads the OS titlebar preferences (button layout and titlebar actions) and pushes changes. The chrome renders from that data: the OS decides which buttons appear, where, and what clicks do; the desktop environment decides the visual style.                      | Realises A5 and the planned `system-appearance` plugin. Each `ts-rs` type names its own output with `export_to`, not a workspace-wide `TS_RS_EXPORT_DIR`, so plugins move between workspaces unchanged.                                                                                                      |
| A16 | Accepted (2026-09-30) | **JavaScript reaches a native plugin only through its `guest-js` package**, enforced by `scripts/check-plugin-boundaries.sh`.                                                                                                                                                                                                                                                              | Command and event names are an implementation detail of the plugin; feature code gets typed functions.                                                                                                                                                                                                       |
| A17 | Accepted (2026-09-30) | **`window-manager` is a reusable plugin for compositor and window-manager features a webview cannot reach**: it reports capabilities (session, Always on Top, system window menu) and asks the compositor to show its own window menu through `gdk_window_show_window_menu` (`xdg_toplevel.show_window_menu` on Wayland). Windows and macOS report the system menu as unavailable for now. | Tauri, tao and wry expose no `show_window_menu`; GDK does. Implements D90. The compositor only honours the request for a recent real button press. Verified by hand on GNOME (Mutter) under Wayland (2026-09-30): the menu appears and its Always on Top works; KDE, X11 and other compositors are untested. |
