## 2. Conventions carried over

- `concurrency: ci-${{ github.ref }}` with `cancel-in-progress: true`; minimal `permissions` (`contents: read`, `packages: read`).
- Rust jobs run in the **`ghcr.io/liminal-hq/tauri-ci-desktop:latest`** container (credentials from `github.actor` and `GITHUB_TOKEN`), with `git config --global --add safe.directory "${GITHUB_WORKSPACE}"`, `Swatinem/rust-cache@v2`, and `taiki-e/install-action@nextest`.
- JS jobs use `oven-sh/setup-bun@v2` and `bun install --frozen-lockfile`.
- Test jobs upload JUnit XML as artefacts plus the `event-file`, always (`if: always()`), for `publish-test-results.yml`.
- Job steps end with a step summary where the result is worth reading (Cadence style).
- Actions are pinned by major version and kept current by Dependabot.
- Canadian English in workflow names, step names and summaries ("artefacts", "synchronised").

**Remote providers (milestone 6, A85).** The shared `waypoint_vfs::conformance` suite runs in `rust-tests` and `windows-tests` against `LocalProvider`, `MemoryProvider` and `FakeRemoteProvider` (`crates/waypoint-vfs/tests/remote_conformance.rs`). Each provider crate adds the same suite against a real server, started by its own tests where that needs no root: the SFTP provider's tests generate keys and run OpenSSH `sshd -D` as the current user on a free loopback port (as spike #278 did), so they run wherever `sshd` and `sftp-server` are installed and skip with a message elsewhere (always on Windows, and in the `rust-tests` container when it has no `sshd`). The same tests also run against an in-process SFTP server (`crates/waypoint-provider-sftp/tests/support/fake.rs`: `russh`'s server and `russh-sftp`'s server trait over an in-memory tree, with passwords and public keys, host-key rotation, refused logins, scripted drops, `readdir` batches and OpenSSH's extensions or none), so `rust-tests` and `windows-tests` (which lists `waypoint-provider-sftp`) exercise the SFTP code, including listing, reading, writing, resuming, the rename fallback, host keys and reconnecting, on every platform and without `sshd`; each shared test body is declared twice, as `name::in_process` and `name::openssh`, and the OpenSSH half stays the check against the real server's behaviour. The listing budget runs against either (`listing_budget::in_process` and `listing_budget::openssh`). The `remote-conformance` job installs `openssh-server` and runs them with `WAYPOINT_SFTP_REQUIRE=1`, so a missing server fails there instead of passing quietly; Samba's `smbd` joined it the same way with the SMB provider (a private state directory and the runner's own account, so the tests need no root; `WAYPOINT_SMB_REQUIRE=1`). The SMB listing and read benchmark (`crates/waypoint-provider-smb/tests/listing_budget.rs`) is `#[ignore]`d too. The listing budget (`crates/waypoint-provider-sftp/tests/listing_budget.rs`) is `#[ignore]`d and run by hand with `--run-ignored only --release`. The archive provider (A91) needs no server either: its tests read archives made by the real `tar`, `zip` and `7z` (encrypted ones included), the job installs them, and `WAYPOINT_ARCHIVE_REQUIRE=1` makes a missing tool a failure there; they skip with a message elsewhere, and the crate's pure tests also run in `windows-tests`.
The Git provider (A101) needs no server: `remote-conformance` also runs `cargo nextest run --profile ci -p waypoint-provider-git` with `WAYPOINT_GIT_REQUIRE=1`, and its tests build repositories with the real `git` (the provider never runs it), skipping with a message where `git` is missing. Its 50 000-file budget is `crates/waypoint-provider-git/tests/budget.rs`, ignored by default like the others. The S3 provider (A104) runs against `rclone serve s3` (the job downloads the current `rclone`; the distribution's is too old to have `serve s3`) and MinIO, with `WAYPOINT_S3_REQUIRE=1`. MinIO is a container pinned by digest and started with the tests' root credentials, reached through `WAYPOINT_MINIO_URL` (MinIO's own images and binaries are no longer public, so the image is Chainguard's build of it, `docker.io/chainguard/minio`; `WAYPOINT_MINIO` names a binary for a local run). MinIO runs the full conformance suite, multipart, folder markers, resume and copies in parts; rclone cannot hold folder markers or answer a multipart upload correctly, so it runs the listing, read, write, copy and error tests. The in-memory server and recorded-fixture tests need no program and also run in `rust-tests` and `windows-tests`. Its 100 000-key budget is `crates/waypoint-provider-s3/tests/listing_budget.rs`, ignored by default like the others.

`bun run validate` is the local mirror of this gate and grows in step with it.

## 4. Release

`release.yml` follows Jar's shape. Nothing in it has run yet: the first tag (a `-beta.N` one, on a fork, #392) is its first test.

1. **Trigger:** push of a tag `vX.Y.Z` or `vX.Y.Z-beta.N`, or `workflow_dispatch` with an optional `release_tag` (a tag that already exists; with none, the tag is `v` plus the synchronised version) and `release_draft`. The tag is checked against a strict pattern before anything uses it, and no event or input value is interpolated into a script (each goes through `env:`). One run per tag (`concurrency`), never cancelled halfway. The workflow's permissions are `contents: read` and `packages: read`; only `prepare-release` and `publish-release` have `contents: write`, and the only secret is the default `GITHUB_TOKEN`.
2. **`prepare-release`:** resolves the tag; requires its commit to be an ancestor of `origin/main`; runs `scripts/check-release-versions.sh --current-version` and requires it to equal the tag without its `v`; marks a pre-release (`-` in the tag); checks the MCP bridge is still compiled out (below); and creates or reuses the GitHub Release. A new release is created as a **draft** whatever the run asked for, so nobody sees one with half its assets; a reused release keeps its state (a public one stays public), and a run with `release_draft` also makes it a draft. It outputs the version, tag, commit, name, pre-release flag, draft flag and release id and URL.
3. **Build jobs** (each checks out the tag's commit, re-checks the version, and stages its files with `actions/upload-artifact` next to a `build.sha256` of them; the Rust cache is restored and never saved, so a release builds from what the tag says):
   - **`build-linux`** (x64 on `ubuntu-24.04`, arm64 on `ubuntu-24.04-arm`, both in the `ghcr.io/liminal-hq/tauri-ci-desktop:latest` container): `scripts/stage-elevate-helper.sh`, then `bun run --cwd apps/waypoint tauri build --bundles deb,rpm --config src-tauri/tauri.package.linux.json`, a check that both packages hold the elevated helper (below), staged as `linux-deb-<arch>` and `linux-rpm-<arch>` (the deb alone, because the AppImage workflow packages the one `.deb` in its artefact).
   - **`package-appimage`:** the shared `liminal-hq/.github` workflow `package-arch-appimage.yml` (pinned by commit) turns each deb into an AppImage on a pinned Arch image with `quick-sharun`, and uploads `appimage-<runner>`. Tauri's own AppImage bundler is not used (`--bundles` never names `appimage`), which keeps the build off the container's experimental `tauri-cli` branch.
   - **`build-windows`** (x64 on `windows-latest`, arm64 on `windows-11-arm`, `shell: bash`): `scripts/stage-elevate-helper.sh`, then `tauri build --bundles nsis --config src-tauri/tauri.package.windows.json`, staged as `windows-installer-<arch>`; then the portable zip, staged as `windows-portable-<arch>`, which holds the `waypoint.exe` that build left in `target/release` (the one inside the installer), `LICENSE-APACHE` and `LICENSE-MIT`, and `WebView2Loader.dll` only if the exe loads it at run time. It registers nothing (A148). macOS is not a target.
4. **`publish-release`:** downloads every artefact, checks each file against its `build.sha256`, requires the eight deb, rpm, installer and zip files and each AppImage that was built (below; the AppImage is optional, A153: one that was not built is a warning, and the job summary names it), copies them under their release names, writes `SHA256SUMS` over those names, uploads with `gh release upload --clobber`, and, unless the run was a `release_draft` one, publishes the release (`--draft=false`; a pre-release is never marked latest).

**Asset names (A152).** `Waypoint_<OS>_<version>_<arch>[_<kind>].<extension>`, where `<OS>` is `Linux` or `Win`, `<version>` is the synchronised version without the `v`, and `<arch>` is `x64` or `arm64` on both systems (not `amd64`, `x86_64` or `aarch64`). The assets of `v1.2.3`:

| Asset                                 | What it is                                  |
| ------------------------------------- | ------------------------------------------- |
| `Waypoint_Linux_1.2.3_x64.deb`        | Debian package (also `_arm64`)              |
| `Waypoint_Linux_1.2.3_x64.rpm`        | RPM package (also `_arm64`)                 |
| `Waypoint_Linux_1.2.3_x64.AppImage`   | AppImage (also `_arm64`)                    |
| `Waypoint_Win_1.2.3_x64_Setup.exe`    | NSIS installer (also `_arm64`)              |
| `Waypoint_Win_1.2.3_x64_Portable.zip` | Portable zip (also `_arm64`)                |
| `SHA256SUMS`                          | `sha256sum` format, over the uploaded files |

The files are as the bundlers produced them: only their names change. `SHA256SUMS` is checked with `sha256sum --check SHA256SUMS` in a folder with the downloads.

**The elevated helper is in the deb, the rpm and the installer, and nowhere else (Open as Administrator, A154).** The helper is only ever started from a place a standard user cannot write to, so each package puts it there and the two copies that cannot (the AppImage and the portable zip) do not carry it and report elevation unavailable.

- **Linux (deb and rpm):** `/usr/libexec/waypoint/waypoint-elevate-helper` (`root:root`, `0755`) and `/usr/share/polkit-1/actions/ca.liminalhq.waypoint.admin.policy` (`root:root`, `0644`), through `bundle.linux.deb.files` and `bundle.linux.rpm.files` in `apps/waypoint/src-tauri/tauri.package.linux.json`. The paths are `HELPER_PATH` and `POLICY_PATH` in `src-tauri/src/elevate.rs`, and the policy's `org.freedesktop.policykit.exec.path` is the same path; a test in that file fails if the three drift. The AppImage is made from the deb by the shared workflow, whose call is unchanged. The helper is added to the deb and not to anything the AppImage workflow is told about, but what that workflow takes out of the deb is its own business (unverified until the first tag): if a copy lands inside the AppImage it is inert, because the app only ever starts the helper at the fixed path above and reports elevation unavailable when run as an AppImage.
- **Windows (NSIS installer):** `waypoint-elevate-helper.exe` beside `waypoint.exe`, through `bundle.resources` mapped to the install folder's root in `tauri.package.windows.json`, which also sets `installMode` to `both`: the plugin offers elevation only when the helper and the app are under Program Files, and Tauri's default `currentUser` installs under `%LOCALAPPDATA%`, where it would never be offered. The installer therefore asks the person to choose: an all-users install (administrator rights to install, under Program Files) enables Administrator access, and a per-user install is unchanged from A148 and reports it unavailable, with the reason. The portable zip packs `waypoint.exe`, the licences and the loader DLL as before and so has no helper.
- **Why separate files:** `tauri-build` checks every configured resource at compile time, so a helper declared in `tauri.conf.json` (or in `tauri.linux.conf.json` or `tauri.windows.conf.json`, which Tauri merges by itself) would fail every `cargo check`, `clippy`, `test` and `tauri:dev` that had not built and staged the helper first. The `tauri.package.*.json` files are merged only by the release jobs, with `tauri build --config`, and a test keeps the base configs free of the helper.
- **Staging:** `scripts/stage-elevate-helper.sh [target-triple]` runs `cargo build --release -p waypoint-elevate-helper` in the job's environment (so with `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=false`, like the app), finds the binary under `CARGO_TARGET_DIR` and the optional triple, copies it to the git-ignored `apps/waypoint/src-tauri/packaging/staged/` (the one path the package files name, on either system and architecture, `0755` on Linux) and prints its SHA-256 and size. The Linux jobs then list the deb with `dpkg-deb -c` (and the rpm with `rpm -qlvp` where `rpm` exists) and fail unless the helper and the policy are there with their owners and modes.

**The MCP bridge is compiled out of every release build.** There is no Cargo feature for it: `tauri-plugin-mcp-bridge` is a dependency (`cfg(not(windows))`) and `lib.rs` registers it under `#[cfg(all(debug_assertions, not(windows)))]`, and `tauri build` is a release build, where `debug_assertions` is off. `release.yml` sets `CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=false` for every build, and `prepare-release` fails the release if `mcp_bridge::init` is no longer registered exactly once under a `debug_assertions` cfg, or if a Cargo manifest sets `debug-assertions` to anything but `false`. The crate is still compiled and linked as a dependency and nothing calls it; the `dev-automation` capability (`mcp-bridge:default`) is in every build's capability set but belongs to a plugin that is never registered. Dropping the dependency from release builds altogether would need a feature, which is not done.

5. **Versioning:** `scripts/check-release-versions.sh` requires one synchronised version (`X.Y.Z` or `X.Y.Z-beta.N`) in the root `package.json`, `apps/waypoint/package.json`, `tauri.conf.json`, the app crate's `Cargo.toml` and `[workspace.package] version` when the root `Cargo.toml` sets one, and in any member that says `version.workspace = true` (which also requires the workspace to set one). With no argument it lists every mismatch and exits 1; with `--current-version` it prints the version and nothing else. It does **not** look at the libraries and plugins under `crates/` and `plugins/` that keep a `version` of their own (today `0.1.0`, not the release version): they are never released alone, and reusable plugins that have graduated are versioned in the shared repo by `covector`, not here. Making a library follow the release is one line (`version.workspace = true`, with `[workspace.package] version` added), and the script checks it from then on. The version is `0.0.0` until the first release.
6. **Signing and Windows packaging:** Windows builds are **unsigned** and there is no signing step in the Windows jobs (D198, A147). Code signing, the sparse MSIX package (and with it the modern Explorer menu, #385) and Windows 10 support are deferred to an undetermined date (`docs/open-questions.md` #8 and #10); when they are taken up, the decision names the certificate's owner and adds one signing step before `SHA256SUMS` is written. What is decided now: the artefact set and the installer format (A148), the app identity (D199, A149) and the channels (D201, A151), and the updater is the spike in #376.

**Not built yet:** the x64 AppImage while it cannot be (A153, #630), the Flatpak job (D200, A150, #390; Flatpak is a packaging follow-up, and portals-first code is written from day one so the manifest is not a rewrite), signing, the updater's feed and signatures (#376), the installer's shortcut and ProgID registration (A148, A149) and any use of the version in About (#393). **Unverified until the first tag:** AppImage packaging of this app (the default runtime packages of the shared workflow are used), the NSIS bundle on both Windows runners (Tauri downloads NSIS itself), the arm64 runner labels, whether the pre-release version suits the installer's version field (A151), and the portable zip.

## 5. Automation and agents

- The debug-only MCP bridge is compiled out of release builds (`#[cfg(debug_assertions)]`, checked by `prepare-release`, §4), so release artefacts never ship it.
- Agents never push, tag, dispatch workflows or edit workflow files without an explicit request (`AGENTS.md`).
