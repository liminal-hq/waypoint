# Front-end framework evaluation and stack

Status: **accepted** · decision A2 in `decisions.md` · confirmed on WebKitGTK by Milestone 0 spike 1 (`milestone-0-spikes.md`); WebView2 and the React Compiler are still to measure

The question: which front-end approach keeps Waypoint's code clean and maintainable over years, for an app that is a dense, keyboard-first, multi-window file manager rendered in a Tauri webview.

## 1. What this app asks of a front end

| Demand                                    | Why it matters here                                                                                                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Very large, frequently updating lists** | A folder can hold hundreds of thousands of entries; selection, rubber-band, type-ahead and watcher updates must stay smooth.                                                                     |
| **A custom drag-and-drop engine**         | Spring-loading, action pickers, tab tear-off, Shelf, drop onto tabs and remotes: pointer-event state machines, not a stock DnD widget.                                                           |
| **Many windows**                          | Each webview has its own JS runtime and heap; startup time and memory per window count, and tear-off spawns them on demand.                                                                      |
| **WebKitGTK as the Linux engine**         | Slower and less capable than Chromium; `backdrop-filter`, transparency and compositing need care. Framework overhead is felt more here.                                                          |
| **Deep accessibility**                    | Listbox/option semantics, menus, dialogs, focus management, live regions (`docs/accessibility.md`). Mature primitives and testing tools help.                                                    |
| **Family reuse**                          | The shared Liminal title bar, context menu (Liminal Notes, Jar), and settings shell (Emoji Nook) are React components. Threshold, Spindle, Cadence, Jar and Emoji Nook are all React/TypeScript. |
| **Maintainability by one small team**     | Boring, well-documented, hireable and agent-friendly beats clever.                                                                                                                               |
| **Rust does the heavy lifting**           | Sorting, filtering, search, jobs and session state live in Rust, which shrinks what the front end must be fast at.                                                                               |

## 2. Options considered

| Option                                           | For                                                                                                                                                                                                                                                                                                                                                  | Against                                                                                                                                                                            |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **React 19 + TypeScript**                        | Same as every sibling app, so the shared chrome, context menu, tokens and hard-won house patterns (routing, testing, Tauri mocks) carry over unchanged. Largest ecosystem for the primitives this app needs (virtualisation, accessible menus, headless tables). React Compiler removes most manual memoisation. Best tooling and agent familiarity. | Coarser update granularity than signals; large lists need disciplined virtualisation and stable row components; runtime is bigger than Solid/Svelte.                               |
| **SolidJS**                                      | Fine-grained reactivity is a natural fit for a huge, constantly patched list; small runtime; fast startup per window.                                                                                                                                                                                                                                | No family reuse (every shared component would be rewritten), a much smaller ecosystem for accessible primitives, a team of one carrying a second UI stack across the org.          |
| **Svelte 5 (runes)**                             | Small output, pleasant authoring, compile-time reactivity.                                                                                                                                                                                                                                                                                           | Same reuse and ecosystem problem as Solid; runes are still settling in tooling; less mature virtual-list and a11y primitive options.                                               |
| **Vue 3**                                        | Good reactivity and DX.                                                                                                                                                                                                                                                                                                                              | No family reuse; no advantage over React for this workload.                                                                                                                        |
| **Rust UI (Leptos, Dioxus, Yew) in the webview** | One language; fine-grained reactivity via WASM.                                                                                                                                                                                                                                                                                                      | WASM/JS boundary cost for DOM-heavy UI, immature accessible-component ecosystem, no reuse of the shared chrome, slower iteration. Not worth it while Rust already owns the domain. |
| **Native toolkit (GTK4, Qt, Slint)**             | Truly native look, no webview limits.                                                                                                                                                                                                                                                                                                                | Abandons Tauri, the family stack and the design system; Windows parity becomes a second port. Out of scope by decision (D42–D46 assume Tauri).                                     |
| **Vanilla / Web Components**                     | No framework lock-in.                                                                                                                                                                                                                                                                                                                                | Rebuilding state, routing and a11y patterns by hand at this scale is the opposite of "clean and well maintained".                                                                  |

## 3. Recommendation

**React 19 + TypeScript (strict) + Vite**, with the performance-critical concerns pushed out of React:

1. **Virtualise everything list-shaped** with TanStack Virtual (rows, grid cells, columns view, sidebar tree, search results) so the DOM holds only the visible window.
2. **Keep large data in Rust.** The front end holds a listing _handle_ and the visible range, not the directory (see `README.md` §3). Sorting, filtering, grouping and search run in Rust.
3. **Use the React Compiler** and stable, memoised row components; rows receive primitives and a row id, and subscribe to selection through a narrow selector so a selection change re-renders only the affected rows.
4. **Keep drag state out of React state.** The drag engine is a plain TypeScript state machine driven by pointer events, writing to a small external store and CSS variables for the ghost/badge position. React renders the discrete states (target highlight, badge text), never every pointer move.
5. **Small entry bundle, lazy feature routes.** The main window loads the shell and browser feature; Settings, plugin manager, Properties, dialogs and the terminal load on demand, keeping new-window startup fast.

**Why not Solid or Svelte despite the technical fit?** The gain is real but modest once lists are virtualised and Rust owns the data; the cost is permanent — a second component library beside the shared Liminal chrome, a second set of accessibility primitives, and a second stack to maintain across the org. If Milestone 0 spike 1 shows React cannot hold 60 fps selection and scroll on WebKitGTK with a virtualised 500 000-row listing after the mitigations above, the fallback is **SolidJS for the file-view surface only** (list/grid/columns) embedded in the React shell, decided then with numbers. Everything else stays React.

### `TabsApi` (milestone 3)

`TabsApi` (`apps/waypoint/src/services/tabsApi.ts`) is the front end's whole view of the session plugin, and it mirrors the plugin's commands one for one: tabs (`openTab`, `closeTab`, `activateTab`, `moveTab`, `navigate`, `back`, `forward`, `pinTab`, `setTabColour`, `setTabHints`, `reopenTab`), groups (`createGroup`, `addToGroup`, `removeFromGroup`, `renameGroup`, `setGroupColour`, `setGroupCollapsed`, `collapseOtherGroups`, `sortGroup`, `duplicateGroup`, `moveGroup`, `ungroup`, `closeGroup`), pairs (`joinPair`, `separatePair`, `setPairLayout`, `setPairSizes`, `swapPanes`, `toggleSplit`), and windows (`openWindow`, `closeWindow`, `setGeometry`, `setView`, `moveTabs`). Commands that make something resolve to its id (a group, a pair, a window label). Every command acts on the calling window; only `moveTabs` and `closeWindow` name another window.

A window's snapshot (`getSnapshot`) is its own tabs, `active`, `mru`, `groups`, `pairs`, `geometry` and `view`, plus the store's `closed` list. Rust sends a window only its own events, numbered by the one global revision, so a window sees gaps; `applyTabsEvent` keeps the rule that an event applies when its revision is above the snapshot's, and applies every event kind (`windowOpened` and `windowClosed` only advance the revision). Closing a tab emits no event for `closed`, so a menu that shows Recently Closed reads a fresh snapshot. `tabsStore` still subscribes first and reads the snapshot second.

Workspaces ride the same channel: `saveGroupAsWorkspace`, `renameWorkspace`, `deleteWorkspace`, `setActiveWorkspace` and `setWorkspaceLocations` are commands, the snapshot carries `workspaces` and the window's active `workspace`, and `workspacesChanged` and `workspaceActivated` events keep them current (`isWorkspaceNameTaken` recognises the typed duplicate-name rejection).

The sidebar's Favourites section does not know whether it shows the shared bookmarks or a workspace: it renders a `FavouritesSource` (`apps/waypoint/src/sidebar/favouritesSource.ts`), a list plus `add`, `remove`, `rename` and `move`, built either over the `PlacesClient` (the bookmarks file) or over `TabsApi.setWorkspaceLocations` (the window's active workspace). Anything that pins a folder from outside the sidebar (the file list's menu, **Ctrl+D**) goes through `useAddFavourite`, so it edits whichever list is showing. The `PlacesClient` contract is unchanged and still owns only the file-backed list.

`FakeTabsApi` is a handle on a `FakeTabsStore`, the TypeScript twin of the Rust store. `new FakeTabsApi()` is the milestone 2 single window; to test a hand-off, share one store: `const store = new FakeTabsStore(); const one = new FakeTabsApi(store, 'main-1'); const two = new FakeTabsApi(store, 'main-2');`. `FakeTabsStore` takes a `createWindow` hook (throwing undoes the change, like a failing `WindowFactory`) and an `onLastWindowClosed` hook. The scripted scenarios in `crates/waypoint-session/tests/conformance/*.json` run against both the Rust store and the fake (`tabsConformance.test.ts`), so the two cannot drift; when they disagree the Rust store is right and the fake changes.

### Grouped listings (D128, A72)

A listing whose sort groups carries its runs in `ListingModel.groups` (from the snapshot, `Changed` events and the scan's last `Progress` event). `GroupLayout` (`browse/groupLayout.ts`) turns the runs and the folded groups into display rows (a header, then lines of entries: one entry a line in the list, `columns` in the grid) by arithmetic, so the virtualisers, scroll offsets, anchoring through a patch, fetching and the scroll cap count headers without building a row per entry. `navigate` (`groupNav.ts`) is the keyboard for a grouped listing: it steps over open headers, stops on folded ones and keeps the column in the grid; an ungrouped listing keeps the views' own `move`. Selection, focus and the anchor stay in entry positions; the browse store adds `collapsed` (by `groupId`, a stable key, so a fold survives patches) and `focusHeader`, and keeps what a folded group hides out of the selection. `groupHeader.ts` holds every heading's words, so the catalogue is the only place they are written. The window's sort and grouping live in `viewStore` (`ViewPrefs.sort`): a new listing opens with them and `ListingManager`'s `onSort` keeps them current.

### Panes and `ListingManager.sync` (milestone 3)

`ListingManager.sync(tabs, visible)` takes the set of tabs that are on screen: the active tab, or every pane of the active tab's pair (`visibleTabs` in `tabs/pairLayout.ts`). Each visible tab has a live listing of its own, with its own selection and scroll in its own `ListingSession`; a tab that leaves the screen is a background tab and evicts as before (A29). The focused pane is the active tab, so `useNavigation`, the path bar, the sidebar and the status bar follow it unchanged; a pane passes its own tab id to `useNavigation(tabId)` so opening a folder there navigates that pane's tab even in the moment before the session has activated it. `app/PaneArea.tsx` renders one pane or a pair's panes; a divider drag resizes in memory and `setPairSizes` is written on release (`PaneDivider`).

The layout is one folder per area at the top of `src/`, not a `features/` folder. Later milestones add areas the same way (`dnd/` for the drag engine, then `ops/`, `shelf/`, `settings/` and `commands/` in milestone 4, then `search/`, `terminal/`, `inspector/` and `extensions/` as they arrive); each area owns its components, hooks, store and tests.

**File drags (milestone 4, slice 12, D110).** `dnd/fileDrag.ts` is the first consumer of `dragSession` for files: `createFileDrag(deps)` gives a session (store `{ phase, pill, target: FileDropTarget, source: FileDragSource }`) and `press(...)`, which the list and the grid call from `useListInteractions` through `FileDragProvider` (`FileDragContext.tsx`, inside `Workspace`; it reads the default rule and the spring delay from `useSettings` as the drag runs and refuses to start while a tab drag has the pointer). The source is `Sources::Selection { handle, spec }` plus the count, the one name, up to three icon groups, the folder and whether it is read-only. Targets are elements marked with `data-drop`, `data-drop-ref` and `data-drop-label` (`dropTargets.ts`: `folder`, `pane`, `place`, `trash`, `crumb`, `tab`, `plus`, `chip`), hit-tested with `elementsFromPoint` on every move; the hit element gets `data-drop-over` and the root `data-file-drag` (what a release does, for the cursor) so no React render happens per move. `dropAction.ts` is the pure default rule and modifier table; `fileDragModel.ts` the verdict for each target (`evaluateTarget`), the pill's words and `NON_POINTER_PATHS`; the planner's `sameVolume` and refusals are cached per (listing, target) for the drag. Springs navigate through `TabsApi` and are undone with `back` / `activateTab`; the source pane's listing is held by `ListingManager.retain` meanwhile. A drop becomes a job through the file commands (`transferTo`, `moveToTrash`) so refusals, conflicts, errors and the Undo toast are the queue's; `openFolders.ts` handles `+` and chips. `DragStack` draws the ghost, `ActionPicker` the right-button and Alt menu. **Native drops and outbound drags (slice 13).** `services/nativeDndClient.ts` is Waypoint's side of `native-dnd` (`status()` as `NativeDndAvailability` with reasons, `startDrag`, `onEnter` / `onOver` / `onDrop` / `onLeave` / `onDragEnded`), with `tauriNativeDndClient.ts` over its `guest-js` and `fakeNativeDndClient.ts` scripting the same events. `FileDragProvider` takes it as a prop (`Workspace`'s `nativeDnd`, main windows only) and `dnd/nativeDndHost.ts` (`connectNativeDnd`) turns this window's events into `createFileDrag(...).beginNative(...)`, which uses `dragSession.beginExternal` (a drag the page does not see, fed positions) and a `FileDragSource` that names files by location (`external`, built by `nativeDropModel.ts` from the `file:` URIs, with the folder they share) instead of by selection; `evaluateTarget`, springs, the planner and the picker are the in-page ones, and a drop is `FileCommands.transferLocations`. When the pointer leaves the visible window (`app/frameMargin.ts`) `fileDrag.ts` hands the drag over: `OpsClient.resolveSelection` (the ops plugin's `resolve_selection`) gives the lossless locations, `NativeDndClient.startDrag` starts the system drag, the in-page drag ends quietly, and `drag-ended` is announced; failures keep the drag in the page. The Shelf (slice 14) adds a target kind: `shelf`, whose drop adds references through `ShelfActions.addSelection` (or `add` for files from outside) and writes no file, and a second source kind: `FileDragSource` is now `SelectionDragSource | LocationsDragSource`: the latter names its files by location (`Sources::Locations`, sent through `FileCommands.transferLocations`, the one entry point for every drop by location) and is made either by `pressLocations` from a Shelf row or, with `external` set, by a drag from outside the window (`nativeDropModel.externalSource`). A Shelf row dragged out of the window hands its locations straight to `NativeDndClient.startDrag` (no `resolveSelection`), and files dropped on the Shelf panel from another application add references through `ShelfActions.add`. Items from the Shelf may be dropped only into folders (the Trash, `+` and chips refuse them), and a finished move removes the entries whose files left.

**The drag engine (milestone 3).** `apps/waypoint/src/dnd/dragSession.ts` is the generic part and knows nothing about tabs: `createDragSession<Source, Target>({ startThresholdPx, announce, clock?, reducedMotion?, sameTarget? })` gives a session whose `begin(start, handlers)` takes `{ pointerId, clientX, clientY, element, source }` and `{ start?, move, drop, cancel? }`. It owns the press (`pending` until the threshold), pointer capture once the drag starts, `Esc` in the capture phase, `pointercancel`, injectable-clock hold timers (`control.hold(key, ms, fn)`), `consumeClick()` for the click that follows a drag, and a vanilla `zustand` store `{ phase: idle | pending | dragging | cancelled | dropped, pill, target, source }` that changes only when the phase, the pill or the target does. The pointer goes to `--wp-drag-x`, `--wp-drag-y`, `--wp-drag-dx` and `--wp-drag-dy` on the root, so what follows the pointer moves without a React render. A pill's text is announced when it changes. Milestone 4's file drags supply their own handlers.

`tabs/tabDrag.ts` is the tab handlers: it measures the strip once (`dragLayout.ts`), works out on each move which outcome is showing (`TabDragTarget`: `reorder`, `holdSplit`, `holdGroup`, `overGroupLabel`, `leaveGroup`, `splitPane`, `newWindow`) with a `preview` of who slides and where the line or bracket sits, and commits it through `TabsApi` on release. `TabDragProvider` (in `Workspace`) holds the one session, so the strip, the pill and the file area's split regions (`SplitZones`, hit-tested by `splitRegions.ts`) read the same store; `useTabDrag` turns the store into per-slot attributes. A pane header's grip uses a second, smaller session (`paneDrag.ts`). `NON_POINTER_PATHS` pairs every outcome with its menu item or key, and a test fails if one is missing.

_The seam for tear-off (slice 10)._ `TabDragProvider` takes an optional `tearOff: TearOffHook` (`update(point, source)` returns the pill to show, `leave()`, `drop(point, source)` resolves true when it took the tabs). The engine calls it only in the `newWindow` phase (the pointer has left the window: coordinates outside the client area, or the document's `pointerleave`, which `useTabDrag` forwards through `handlers.leftWindow()`; `TabDragDeps.viewport` is the window size). `TabDragSource` carries the unit being dragged (`unit`, `kind`, `group`) and the strip's measurements, so the hook can build the ghost payload and decide merge or new window. The plugin is not imported by the engine.

_Where a foreign drop lands (slice 16)._ The window under a drag from another window draws its landing line from a pure slot computation (`tabs/landing.ts`: the raw slot from the pointer or a drop region, then the store's own ordering on stand-ins for the arriving tabs), fed by a hook that merges the two event sources into one hover (`useMergeLanding`) and a small zustand store the strip reads through `MergeLandingContext`. The line, the drop regions and the merge share that one computation. See `docs/tauri-tear-off.md`.

**The operations queue (milestone 4, slice 06, A56).** `OpsClient` (`services/opsClient.ts`) is the contract over the `waypoint-ops` plugin, with `createTauriOpsClient()` over its `guest-js` and `FakeOpsClient`, which keeps the queue's state machine in memory (a test reads the transition table from the header of `crates/waypoint-ops/src/queue.rs` and fails when the fake differs) and is scripted by `start`, `tick`, `done`, `fail`, `askConflicts`, `askError`, `settleCancel`, `dropNextEvents` and `setRecoveryReport`. `createOpsStore(client)` holds an `OpsSnapshot` mirrored with revision gating like the tabs store: it subscribes to events and progress first and reads the snapshot second, holds events that arrive meanwhile, ignores stale ones, and reads a fresh snapshot when an event shows a miss (a change to an unknown job, an order naming other jobs, a journal revision that skips; a gap in the queue's revisions is normal, since progress ticks use them up). Progress arrives on the window's `Channel`, is kept apart from the revisioned state and flushed once per animation frame, and a tick is used only while it is newer than the job's last event. Selectors give the running and unfinished counts, the most urgent state (waiting, failed, running, done), overall progress by bytes or items, and the jobs that put things in a folder; `submitJob`, `undo`, `redo` and `jobsTargeting` on the handle are what the file commands call, and `runUndo` and `runRedo` in `opsNotices.ts` add the refusal notice. `OpsProvider` gives a window its store; `MainOps` is the Main window's (the ring, the Undo toast for jobs the window started, the announcer for the same, the one-time recovery notice, and Pop out through the app's `open_ops_window` command), and `OpsScreen` is the Operations window's (every job, its own live region, no Show in folder). The dialogs that answer a waiting job register with `registerResolver`, which the row's Resolve… button calls.

**The file commands (milestone 4, slice 07).** `ops/fileCommands.ts` builds each `JobRequest` from the active pane's selection as `Sources::Selection { handle, spec }` (Rust resolves the paths), with the open folder as the destination and the window's label as `originWindow`, and `commandStates` says which commands a listing offers: commands that write are hidden when the listing's `readOnly` flag (added to `ListingSnapshot` from a new `Provider::read_only()`) is set, and Undo and Redo are always listed and disabled when the journal has nothing. The dispatcher waits for its job in the `opsStore`, then finds what it made in the listing: a create's name is the job's `sources.first` (the planner's first free name), a duplicate's copies are the entries the listing gained (`InsertTracker` follows the inserted positions through later patches), and a rename's is looked up by its new name (`reveal.ts`). Inline rename (`browse/InlineRename.tsx`) is driven by the browse store's `renaming` id, validates with `nameRules.ts` (a TypeScript mirror of `validate_name` tested against the table `crates/waypoint-vfs/tests/fixtures/name_rules.json`, which the Rust test reads too), plans the rename first so a taken name is refused without a failed job, and ends on Enter, Escape or a blur to another element. Keys live in `useFileShortcuts` beside `useTabShortcuts`; a field, menu or dialog keeps its own keys. `tabs/closeGuard.ts` is the D29 guard `createTabActions` runs before closing a half of a pair.

**The Settings window (milestone 4, slice 18, A57).** `SettingsClient` (`services/settingsClient.ts`) is the contract over the `waypoint-settings` plugin, with `createTauriSettingsClient()` and `createFakeSettingsClient()`, which keeps Rust's contract (range validation, a rising revision, an event to every listener, `failNext` for a refused save). `settings/settingsStore.ts` mirrors the document the way `opsStore` mirrors the queue: it subscribes before it reads, applies a snapshot or event only when its revision is newer, and changes only by what Rust says is in force (`save` returns the answer and a refusal leaves the store as it was). `useSettings(select)` reads part of it and falls back to the defaults outside a provider, so a component works in a test or a window without the plugin; every Main window gets a `SettingsProvider` from `MainSettings` in `main.tsx`, and the browser reads `clickMode` through it. The `settings` label routes to `app/SettingsScreen.tsx`, which is code-split with `React.lazy` so the main windows do not carry it, and shows the shared `SettingsShell` over the pages in `settings/settingsSections.tsx`; a page that is not built yet is absent, not a placeholder. `SettingsEditorProvider` gives the pages the combined view (the settings document, the operations plugin's own `OpsSettings` through its `get_settings` and `set_settings`, and the native drag and drop status) and saves one change at a time, each made from the answer to the one before, so rows show what Rust says is in force and a refusal appears under its row (`SettingsRow`'s `error`). Number rows commit on Enter or blur (`NumberRow`'s `commitOn="commit"`) so a half-typed value is never saved. `Ctrl+,` opens the window from any Main window (`settings/openSettingsWindow.ts`, over the app's `open_settings_window` command); the application menu and the command palette will call the same function.

**The clipboard, Copy To… and the other pane (milestone 4, slice 10).** The clipboard is Rust's and every window follows it. `ops/clipboardService.ts` mirrors the plugin's `Clipboard` in a store by revision (`OpsClient.onClipboard` and a first read race, the newer wins), puts a selection on it with `setClipboardFromSelection` (Rust resolves the locations, so the page never builds a path) and keeps the system file clipboard level through an injected `OsClipboardClient` (`native-dnd`'s `set_files` and `get_files`, `FakeOsClipboardClient` in tests): Copy and Cut also set it, and a paste, the window's focus and the plugin's change event look at it and adopt files another application copied, by the rule in `ops/clipboardRules.ts` (`chooseClipboard`, D107). `clipboardRules.ts` holds the other pure rules too: `cutNames` (the rows a cut dims, by name within a folder's `uri`; `ListView` and `GridView` set `data-cut` from `useCutNames`), `pasteRefusal` (a folder into itself, a cut onto its own folder), `pasteRequest` (a cut moves, a copy beside its originals is a `duplicate`, everything else copies, with no conflict policy so the resolver asks). `fileCommands.ts` gains `cut`, `copy`, `paste(session, into?)`, `copyTo`, `moveTo`, `copyToOtherPane` and `moveToOtherPane`; the last two are F5 and Shift+F5, which fall back to the dialog when `otherPane` (`ops/otherPane.ts`, the next pane of the pair) is absent or read-only. The destination dialog is `ops/DestinationDialog.tsx`: `destinationModel.ts` has Rust parse and check what was typed (`parseLocation`, then the new `VfsClient.checkFolder` over the vfs plugin's `check_folder`) and keeps the recent folders; `destinationStore.ts` is `pickDestination(options)`, a promise-returning question the window's `DestinationHost` answers (it builds the lists from the places, the tabs and the recent folders, and makes New Folder… through the queue). `pickDestination` is the one place anything that needs a folder asks (the conflict dialog's "Choose another location…" and drops use it). The menus gain the clipboard and transfer items in `EntryContextMenu` and `BackgroundContextMenu`, hidden or disabled by `commandStates` (`reads`, `writes`, `paired`, the clipboard's size), and the menu-key parity test in `browse/fileMenus.test.tsx` covers the new keys.

**The sidebar (milestone 2).** `apps/waypoint/src/sidebar/` holds a Places / Folders switch over two views: Places with Favourites, or the Folders tree on its own. Its state is split the way the rest of the window is: Rust owns the Places and Favourites (the `waypoint-vfs` places service, which reads and writes the freedesktop bookmarks file), reached through the `PlacesClient` contract in `services/` (`createTauriPlacesClient()` over the plugin's `guest-js`, `FakePlacesClient` for tests and `?demo`) and supplied to the window by `PlacesClientProvider`. The plugin has no change event, so the client announces each of its own mutations and the sidebar re-reads when the window regains focus to catch edits other programs make to the bookmarks file. The window-only state (panel shown, which view, collapsed sections, expanded folders) lives in a zustand store (`sidebarStore`), in memory and never in `localStorage`. The Folders tree is lazy: a `FolderTreeModel` opens one folders-only listing (`Filter.only = 'directories'`) per expanded node through `VfsClient`, keeps it open while the node is expanded so the tree follows changes on disk, and closes it when the node collapses or the Folders view is left. The tree is its own view so that choosing a place or favourite never moves it: it follows the active tab only while it is the view on screen. The tree never parses a path: its root and the ancestors it expands come from `describeLocation`, and each child's location from `entryLocation` (A28).

**The conflict resolver (milestone 4, slice 09).** `ops/OpsResolverHost.tsx` is the one place a window answers a job in `Waiting`, mounted inside the queue's provider in `MainOps` and in the Operations window. It registers the function behind `requestResolve` (`resolveHook.ts`), which opens `ConflictDialog` or `OperationErrorDialog` by the job's `WaitReason`, and it opens a dialog by itself for the jobs whose `originWindow` is the window's label, so each question has one answerer; "Resolve…" asks for it from any window. A dialog stays open only while its job is `Waiting`: a wait that ended elsewhere closes it, and a new wait (a clash met inside a merged folder) opens a fresh one. `conflictModel.ts` holds the rules (legal choices per `ConflictKind`, bulk coverage, the `resolve` arguments), `problemModel.ts` the words and decisions for each `OpsError`, and both are tested apart from the components. The Trash's restore questions go through the same dialogs; `OperationErrorDialog` has an `onChooseLocation` hook for "Choose another location…" that stays unused until a destination picker exists in the window.

**The Devices section.** `apps/waypoint/src/devices/` is the sidebar's Devices section (A62, A69, D120). `DevicesClient` is injected (the Tauri implementation over `@liminal-hq/plugin-volumes`, `FakeDevicesClient` for tests and `?demo`) and supplied by `DevicesClientProvider`. `useDevices` reads the plugin's status, then the list, then follows `volumes://changed`: it subscribes first, ignores an event whose revision is not above the last seen and drops a list read that an event overtook, so a stale list never replaces a newer one. Actions come from the volume's `can*` flags filtered by the plugin's `getStatus` features (`actionsFor`), so an option that cannot work here is hidden and the section itself is not shown when `list` is unavailable; the Services panel already reports the plugin. `deviceModel.ts` holds the pure parts: usage text and percentage, which volumes get a row, and the sentence for each `VolumesError` (a busy volume names what holds it). Announcements and failures go to the sidebar's polite live region and the status bar notice. The Unlock dialog keeps the passphrase in component state only and offers no way to remember it.
**Thumbnails.** `apps/waypoint/src/thumbnails/` is how the views draw thumbnails (A61). `ThumbnailsClient` is injected and `ThumbnailsProvider` reads the plugin's status once; `useActiveThumbnailsClient` is `null` (so every view keeps its icons and asks for nothing) when there is no client, the plugin reports itself unavailable or Settings → Previews & thumbnails → Show thumbnails is off. A view makes a `ThumbnailLoader` for its listing handle and size (`useEntryThumbnailLoader`; the Shelf uses `useLocationThumbnailLoader`) and `useViewportThumbnails` calls `want(visible, near)` whenever the range actually in view (the virtualiser's `range`, not the overscan) or the listing changes. `thumbnailPositions` orders the request: in view first, a screen after, a screen before nearest first. The loader asks only for keys it has not asked for, sends the new ones as one batch, calls `prioritise` for the batches that still hold something in view (only when the order changed), cancels a batch when nothing it holds is wanted and forgets its unanswered keys so they can be asked for again, keeps what arrived (and what failed or was skipped, so it is not asked again) and withdraws everything on `dispose`, which is when the view unmounts. A key is `{entry id}:{modified time}` so a changed file is a new request; the page never sends a path, only a listing handle and ids (or a `Location` for the Shelf) to the `thumbnails_*` commands in `apps/waypoint/src-tauri/src/thumbnails.rs`. `wantsThumbnail` leaves folders, sounds, archives and source files alone. `Thumbnail` draws the icon in a frame of the caller's size and the `thumb://` picture over it (`alt=""`, not draggable, hidden if it fails to load, faded in with the global reduced-motion rules applying); the list shows pictures only when its measured row height is 40 px or more. The drag stack's front card takes the picture the pressed entry (or each Shelf item, up to three) had already loaded, so a drag never waits for one. The main windows' capability grants the plugin's `get-status` only, so the page cannot ask the plugin about a path itself.
**Quick Look.** `apps/waypoint/src/quicklook/` is the preview overlay (D132, A69), a modal `Dialog` inside the window, not a window. A view's Space handler (in `useListInteractions`, so the list and the grid cannot drift) asks `quickLookStore` to open with its listing session, its own `move` function and its `onOpen`; the store refuses when no `QuickLookHost` is attached (a window without a `DetailsClient`), so Space then does nothing. The host is mounted once in the workspace and the overlay previews the listing's focused entry, so stepping is a focus move (`moveTo` and `requestScroll`) and a patch that moves the entry moves the preview with it, and the list is already on the right entry when the dialog returns the focus to it. Stepping reuses the view's `move` for Up and Down (so the grid goes a row) and steps Left and Right by one, skipping entries that are neither files nor folders. `previewKindOf` decides from what the listing already knows (group, extension) so nothing waits on a round trip: images use the `wpfile` address over their thumbnail, text reads `readTextHead` (a `notText` rejection falls back to the facts), audio and video are native elements with controls, and everything else is the large thumbnail with the name, kind, size and time. Any failure (an image that does not decode, media that cannot play, an unreadable text) swaps in the facts panel with a sentence. The overlay makes a `ThumbnailLoader` at `x-large` and calls `want(current, neighbours)`, so only the neighbours' thumbnails are fetched ahead of a step. The `DetailsClient` reaches the overlay through `DetailsClientContext`.
**Open With.** `apps/waypoint/src/openWith/` holds Open With's front end. `OpenWithClient` is injected (the Tauri implementation over the `mime-apps` guest-js package, with the chooser parented to the window; a fake serves tests) and `OpenWithProvider` reads the plugin's status once so everything below can hide what does not work. `useOpenWithMenu` resolves the right-clicked entry or the selection it is part of to URIs, reads `handlers` for them and gives `EntryContextMenu` the submenu (a disabled row first, then the applications, so the menu does not change shape); `openWithMenu` decides what is offered from the features and the `mixed` flag, and `startOpenWith` starts an application and turns a failure into a notice. `Other Application…` opens `OpenWithDialog` through a small store (`OpenWithHost`, mounted in the workspace like the destination dialog) or, for one file where the plugin has a chooser, calls `choose`. The `openWith` command in the registry (File menu and palette) acts on the active pane's selection and is hidden unless the plugin can list applications or choose.

**The Trash view.** `apps/waypoint/src/trash/` holds the Trash's front end. `TrashClient` is injected: it reads the Trash's info, submits jobs, follows job events; the Tauri implementation sits over the vfs and ops guest-js packages and a fake serves tests. `useTrashInfo` reads the item count on mount, on window focus, whenever a job finishes and every 10 seconds while the window is visible. `useTrashJobs` holds the confirm state, submits `Restore`, `Delete` and `EmptyTrash` jobs and follows each one it started to report how it ended (a Restore's conflict or missing-folder question is asked by the shared resolver below); the workspace provides its actions through a context that `useTrashActions` reads, so the sidebar, the menus and the strip above the list share them. `ListView` chooses its columns from the snapshot: when `ListingSnapshot.layout` is `trash` they are Name, Original location, Date deleted and Size (Original location is not sortable); `readOnly` is carried on the listing for the views that will offer writes, and nothing in the Trash does. The entry, background and sidebar menus differ in the Trash, and a Trash that cannot be browsed shows an explanatory unavailable state in place of the list.

Rules that keep it clean: areas import from `services/`, `theme/` and `packages/chrome`, and from each other only through the file that defines the thing, never an area's internals; an area exposes its public surface through the file that defines it (no barrels); extension-point _slots_ (column, panel, statusItem, action) are rendered by the owning feature from the registry the extension host provides.

## 6. Shared chrome

`packages/chrome` implements `docs/shared-components.md`: the unified title bar (slots `start` / `center` / `end` / `controls`, drag regions, maximised hook, Always on Top, platform control layout, transparency awareness), the shared window menu, the Liminal context menu, the modal `Dialog` and `ConfirmDialog` (native `<dialog>`, no dependency), and the settings shell (`SettingsShell` with its rows). It is built domain-free and consumed through workspace imports first, so it can be extracted to a package the other Liminal HQ apps adopt (open question 2). Extraction is a follow-up decision (A5), not a milestone-1 dependency.
