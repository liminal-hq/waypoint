# Theming & Platforms

## Theme axes

1. **Colour scheme:** Light, Dark or System (the portal's `org.freedesktop.appearance color-scheme`).
2. **Theme source:** _Liminal_ (brand tokens) or _OS_ (portal accent-color plus the GTK/Qt palette hints). This follows the Emoji Nook approach, which detects Adwaita or Breeze.
3. **Accent:** the OS accent, the Liminal ember, or a custom swatch.
4. **Density:** Comfortable or Compact.
5. **Match the system's colours:** off by default; takes surfaces, text, selection, borders, focus and the status colours from the OS palette (D144). See _The OS palette_ below.
6. **Icon theme:** Waypoint's own set (the default), Portage (a coloured set) or the OS theme (freedesktop lookup, Windows shell icons). The Waypoint set is also the fallback. See _File and folder icons_ below.

## File and folder icons

Icon themes apply to file and folder icons only; the toolbar, menu and chrome icons are always Waypoint's own, and they follow the icon style (below). Rust gives every entry an `IconGroup` (31 of them, see D138) and, for the user's standard folders, a `special` marker, and a set maps those to artwork, so a new set needs no new classification.

- **Waypoint:** the outline set, 16 by 16 glyphs drawn in `currentColor` (`apps/waypoint/src/icons/waypointFileIcons.tsx`). Each standard folder is the plain folder shape with a small inner mark. It is the default, the same on every system, and the fallback for any set that has no icon for a group.
- **Portage:** a coloured set of flat shapes with a lighter lower band, a white highlight at the top left and a soft shadow, drawn in a 64 by 64 box (`apps/waypoint/src/icons/portage/` and `portageIcons.ts`). The art comes from the Portage board of the Claude Design project; it was rendered once, tidied by a throwaway script and committed as static SVG, so nothing from the prototype's code is in the repository. File types are 30 standalone SVGs in `portage/files/` with their own gradient and filter ids (several can share a page), imported as text. Folders are not files: `portageFolderSvg({ colour, tone, variant, badge, glyph })` draws any of them from a few outlines and a palette (`portagePalette.ts`: ten colours, each with a `dark` tone for dark surfaces and a `light` one, and the Rainbow gradient stops), with `closed`, `open` and `empty` variants, seven badges and the ten standard-folder glyphs (`portageFolderArt.ts`). `portageIcons.ts` maps every `IconGroup` and `SpecialFolder` to that art, and `PortageIcon` draws it at a `size` (16 by default) as a decorative inline SVG. `other` has no icon of its own in the prototype; Waypoint draws a plain blank page of the same shape for it (`files/blank.svg`) so an unclassified file does not wear a question mark, and Portage's own "Unknown" page stays in the set for later use.
  - To add a file type: draw it in the same box with the page shape, a coloured label and a white glyph, save it as `portage/files/{name}.svg` with ids that start `pt-{name}-`, no strokes on filled shapes, and no text (draw letters as paths), then add it to `portageFiles.ts` and map the group in `PORTAGE_FILE_ART`. To add a folder colour, a badge or a glyph, add an entry to the palette or to `portageFolderArt.ts`; the tests check every combination for valid SVG, unique ids and no external references.
- **System:** the icons the operating system draws for a type of file and for folders (#218, D143). The icon is asked for by _type_, never by file: `systemIconTarget` (`apps/waypoint/src/icons/systemIconTarget.ts`) turns an entry into its extension (`{ extension: 'pdf' }`), or, for a name with no extension to go by, the stand-in content type of its `IconGroup` (`GROUP_TYPES`: `image/x-generic`, `application/pdf`, …), or for a folder its kind (`{ folder: 'downloads' }`: the standard folders, else `plain`). The reusable `mime-apps` plugin serves the picture on `typeicon://` (see _System icons_ in `os-integrations.md`); the page asks at a size bucket (16, 24, 32, 48, 64, 96, 128 or 256 CSS pixels, from the `size` a view passes to `FileIcon`) and a whole device pixel ratio. `icons/systemIcons.ts` is one store for the window: whether the plugin can supply type and folder icons (and the sentence for why not), the icon theme the OS reports, a revision, and which addresses have loaded. One `Image` probe per distinct address serves every row that shows it, so a listing of ten thousand files makes a handful of requests; a row draws the Waypoint glyph until its address has loaded and for good when the plugin answers 404, and a loaded one as an SVG `<image>` in the glyph's own frame so every rule that sizes a glyph sizes it. When the OS reports a new icon theme or colour scheme (the `system-appearance` change event, listened to by the page, since plugins never call each other) the store asks `mime-apps` to forget its icons, raises the revision (part of every address, so the webview's own cache is bypassed) and repaints; the window's own light or dark tone is in the address too. The toolbar, menu and chrome icons never change.
- **The setting.** `appearance.iconTheme` (`waypoint`, `portage`, `system`; default `waypoint`) and `appearance.folderColour` (the ten ids of `FOLDER_COLOURS`; default `liminal`) are in `AppearanceSettings`, and a document from before them loads with both defaults. `resolveAppearance` turns them into `data-icon-theme` (`system` staying `system`, which draws the Waypoint glyph wherever the plugin supplies none) and `data-folder-colour` on the root next to `data-theme`; `icons/iconTheme.ts` reads those three attributes (one `MutationObserver`, and the OS dark query where no scheme is resolved) through `useIconLook()`, and `FileIcon` renders `PortageIcon` or the Waypoint glyph from it, so the list, the grid, the sidebar, the Shelf, the drag stack, thumbnail placeholders and the Inspector all follow a change live with no remount. The tone is `dark` when the window resolves to dark and `light` otherwise. The Rust and TypeScript colour lists are tested to agree.
- **Cost.** Each distinct icon (a group, or a folder's standard folder, colour, tone, variant and badge) is built once and memoised, so a listing of thousands of rows shares a handful of strings. Portage's shadow, a blurred ellipse drawn with an SVG filter, is off by default (`shadow` on `portageIconSvg`, `portageFolderSvg` and `PortageIcon`): the filter and the ellipse are not in the output, which keeps the markup small and spares a filter pass per row.
- **The icon style.** `appearance.iconStyle` (`light`, `regular`, `bold`, `filled`; default `regular`) reaches the root as `data-icon-style` beside `data-icon-theme`. `theme/tokens.css` turns it into two tokens that every outline icon reads: `--wp-icon-stroke`, the stroke width in a 16 px box (Light 1 px, Regular 1.3 px, Bold 2 px; computed as `max(--wp-icon-weight, --wp-icon-weight-min)`, and high contrast raises `--wp-icon-weight-min` to 1.6 px so no style draws thinner strokes than it needs), and `--wp-icon-fill` (`none`, or under Filled a 30% tint of the icon's `currentcolor`, 40% under high contrast), with `--wp-folder-fill` the folder's accent tint (25%, or 45% under Filled). The glyph frames (`Glyph` in `AppIcons.tsx`, `FileIcon.module.css` and the chrome's `icons.module.css`) set `stroke-width: var(--wp-icon-stroke)` and `fill: var(--wp-icon-fill)` on `[data-fill]`; the chrome defines defaults for both in its `tokens.css` (`1.25px` and `none`) and imports nothing from Waypoint. Only a closed shape carries `data-fill`; an open stroke never does, so Filled cannot draw a chevron or a check as a wedge, and a shape that must never fill sits under `data-outline` (the marks on a standard folder). `expectFillableIcons` (in the chrome) audits every icon module: each element must be marked, an open stroke or under `data-outline`, so a new icon cannot ship without choosing. Grid, Inspector hero and empty-state icons are drawn at larger sizes, so the grid and the hero keep strokes in screen pixels (`vector-effect: non-scaling-stroke`) and the empty state takes a fraction of the weight. Portage ignores the style: the style rules skip `data-icon-theme='portage'`. An element with `data-icon-style-preview` draws in that style whatever the window is set to, which is how the Appearance page shows each option.
- **The page.** Settings → Appearance → Icons has the theme picker (a radio group of cards, each with a preview strip drawn by that set), the folder colour row (ten named swatches in a radio group, shown only for Portage, with a note saying why they are hidden for Waypoint) and the Icon style row (a radio group of cards, each with a strip of a folder, a file and three toolbar and menu glyphs drawn in that style), dimmed while Portage is chosen. The radios move with the arrow keys, Home and End, and the chosen card and swatch carry a tick as well as the accent border.
- Folder badges (version control, remote, encrypted, cloud, link, shared, Trash) and open and empty folder states are drawn by Portage only; the Waypoint set has neither.

**[eng]** Where the OS preferences come from: each window's `ThemeRoot` listens to the `system-appearance` plugin's `appearance-changed` event, then reads `get_appearance` (so a change made while starting is not lost), and lays the answer over the webview's media queries through `theme/pluginAppearance.ts`. A preference the plugin has no source for (its `sources` entry is empty), a failed call and a missing plugin all leave the media-query value in place. The settings still win: an explicit colour scheme, contrast, motion or transparency choice replaces the OS value, the accent applies only when the accent setting follows the system (through the contrast picker, so the text on it keeps 4.5:1), and `--wp-text-scale` is the larger of the Settings text size and the OS text scale, which is limited to 1–3×.

## The OS palette

`system-appearance` has a palette API beside the appearance one (A76): `get_palette()` and `system-appearance://palette-changed`, following the same revision rules. Each of fourteen colours (`windowBackground`, `windowForeground`, `viewBackground`, `viewForeground`, `surfaceBackground`, `selectionBackground`, `selectionForeground`, `border`, `focus`, `warning`, `error`, `success`, `titleBarBackground`, `titleBarBackgroundEnd`) carries the `source` that supplied it or a typed `reason` and a detail.

| Platform                            | Source                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GNOME, Cinnamon, MATE, Xfce, others | The GTK theme's named colours through `StyleContext::lookup_color`, asked on the main thread: `theme_bg_color`, `theme_fg_color`, `theme_base_color`, `theme_text_color`, `theme_selected_bg_color`, `theme_selected_fg_color`, `borders`, `warning_color`, `error_color`, `success_color`, and where the theme has them `popover_bg_color` (or `card_bg_color`) and `accent_bg_color`. The title bar's top is `headerbar_bg_color` and its bottom is `headerbar_shade_color` (or `headerbar_darker_shade_color`), the translucent shade laid over the top and flattened onto it. A name a theme lacks is a miss. The portal's accent fills the selection and focus when the theme gave none.                                    |
| KDE                                 | `kdeglobals`: the `BackgroundNormal` and `ForegroundNormal` of `[Colors:Window]`, `[Colors:View]`, `[Colors:Button]` and `[Colors:Selection]`, `DecorationFocus`, and the `ForegroundNeutral`, `ForegroundNegative` and `ForegroundPositive` of `[Colors:View]`. The title bar's top and bottom are the `BackgroundNormal` and `BackgroundAlternate` of `[Colors:Header]`. It has no border colour. A profile with no colour sections falls back to the GTK theme.                                                                                                                                                                                                                                                               |
| Windows                             | `UISettings.GetColorValue` (`Background`, `Foreground`, `Accent`); in a high-contrast theme `GetSysColor` overrides with the user's own colours. The title bar's top is the accent (`UIColorType.Accent`) when the user turned on accent colour on title bars (`HKCU\\Software\\Microsoft\\Windows\\DWM\\ColorPrevalence` is 1), and in high contrast the `GetSysColor` caption colours (`COLOR_ACTIVECAPTION` and `COLOR_GRADIENTACTIVECAPTION`). Windows has no surface, selection-text, border or status colour outside high contrast, and no title bar colour when the title bar follows the theme. **Type-checked for Windows only; not yet run there. The title bar colour has been neither compiled nor run on Windows.** |
| macOS and others                    | Every colour is unavailable (`platformUnsupported`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

**[eng]** The page reads the palette in each window's `ThemeRoot` (listen, then read, newest revision wins), whether or not the option is on, so Settings knows whether to offer the switch. `theme/palette.ts` maps it onto the tokens as inline custom properties on the root, which the stylesheet's own values never beat: the window and content backgrounds (`--wp-solid-window`, `--wp-solid-content`), the raised surface (the palette's, else the view's), the sidebar and hover (the window colour mixed 4% and 9% toward its text), the selected row (the selection colour), the border (the palette's, else the window mixed 18% toward its text), primary text (the view's text), secondary and muted text (the primary mixed 25% and 40% toward the window) and the danger, success, warning and focus colours (the palette's, else Waypoint's own for that variant, kept in `FALLBACK` and tested against `tokens.css`). Then `liftToContrast` holds each pair to its floor: it moves a failing colour in small steps away from the backgrounds it sits on (lighter on dark, darker on light) until every pair passes, so the result is the nearest passing colour on that line, and returns the pairs it moved. Text keeps 4.5:1 against the window, content, raised, sidebar and hover surfaces; the selected row's background keeps 4.5:1 against the primary and secondary text (the background moves, so the text stays one colour everywhere); the status colours keep 4.5:1 and the focus ring 3:1 against the window, content and raised surfaces. Borders carry no floor, as Waypoint's own are quiet. The title bar is shaded in two tones where the OS reports a title bar colour: the chrome tokens `--wp-title-bar-top` and `--wp-title-bar-bottom` (and `-unfocused` pairs, the focused tones mixed halfway to the window colour) are set only then, and the title bar draws `linear-gradient(to bottom, top, bottom)` from them. Each defaults in `packages/chrome/src/tokens.css` to the flat `--wp-bg-chrome` (or `--wp-bg-chrome-unfocused`), so a theme or platform with no title bar colour draws exactly today's flat bar, and a top with no bottom is flat in the OS's colour. Each tone keeps 4.5:1 against the title's text (primary when focused, muted when not); a tone that fails is lifted like any other and listed. A surface that should sit inside the title bar's shade reads `--wp-title-bar-bottom` (and `--wp-title-bar-bottom-unfocused`): the tab strip does, so it continues the title bar with no seam (in a translucent window it takes the title bar's opacity), its unselected tabs are 45 % of the window colour over it, and its selected tab is `--wp-bg-window`, the navigation bar's own colour. Tab titles stay in the primary text colour, the one held to 4.5:1 on both the window colour and the title bar tones. The accent is not part of the palette: D114 and the accent setting decide it as before.

The palette describes one variant, taken from its window background's luminance. `decidePalette` draws it when the option is on, the palette is usable (a window background and its text are known), high contrast is not in force and the colour mode is System or the variant the palette is; in System mode `data-theme` takes the palette's variant so scrollbars and form controls agree with it. Otherwise it reports why (`off`, `unavailable`, `high-contrast`, `other-variant`) and Waypoint's own colours stay. `ThemeRoot` publishes that decision, whether the system has a palette and the lifted colours to `theme/paletteReport.ts`, which the Appearance page reads: it hides the switch until a palette is known to exist, and shows a note when colours were lifted, when high contrast is in force and when the mode is forced to the other variant. The Services panel lists `palette` under `system-appearance` when it works and gives its reason when it does not.

## Tokens (semantic)

`bg.window`, `bg.sidebar`, `bg.content`, `bg.raised`, `bg.hover`, `bg.selected`, `border.subtle`, `text.primary`, `text.secondary`, `text.muted`, `accent`, `accent.fg`, `danger`, `success`, `warning`, `focus.ring`.
Brand values come from the liminal-hq site tokens (ember accent, warm neutrals, Space Grotesk for display, a system UI font for body). They're defined per scheme.

## Transparency (headline setting)

| Control                        | Range                                                                                                   | Default                                                |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Enable transparency            | on/off                                                                                                  | off                                                    |
| Opacity per part               | 40–100 % each: title bar and menu bar, tabs and toolbar, sidebar, file area                             | 82 %, 90 %, 94 %, 98 %                                 |
| Background blur                | off / low / high (where the compositor supports it: KWin, Mutter with an extension, Win11 Mica/Acrylic) | low                                                    |
| Regions                        | Title bar · Tabs · Sidebar · Content · Inspector                                                        | Title bar, tabs and sidebar translucent; content solid |
| Menus (context menus, pop-ups) | on/off, own opacity 60–100 %                                                                            | on, 96 %                                               |
| Solid when unfocused           | on/off                                                                                                  | on                                                     |
| Tint                           | Neutral, accent, or wallpaper-derived                                                                   | Neutral                                                |

Guardrails: no part of the window is more see-through than keeps its text at 4.5:1 over the worst backdrop (the floor, a pure function in `theme/transparency.ts`: black behind a light window, a light grey behind a dark one, worked out from the theme's own colours; it comes to roughly 40 to 55 % for the built-in themes, and a pure white wallpaper under a dark window can still dip below). Transparency is disabled under reduced transparency or high contrast, until the platform reports that windows can be see-through, and while the window is not in front when "Solid when unfocused" is on. The live preview in Settings draws a sample window over a bright, busy wallpaper with the same function the real windows use. As built (milestone 5): the regions are three switches (title bar and the rows under it, sidebar and panels, file area), each part has its own opacity (`opacity`, `rowsOpacity`, `sidebarOpacity`, `contentOpacity`; D135), the page has a Reset to defaults button that leaves the enable switch alone, menus default to solid, the blur setting is Off, Low or High, and the tint control is not built.

**[eng]** Every window is created transparent (`transparent: true`, frameless) whatever the setting, which the rounded corners need; the setting only changes the alpha of the page's backgrounds (`ThemeRoot` writes `--wp-alpha-*` on the root under `data-transparency='on'`, and `tokens.css` mixes the solid `--wp-solid-*` colours with them) and what `src-tauri/src/effects.rs` asks the `window-effects` plugin for (blur on KDE, Mica or Acrylic on Windows). A window root paints nothing while the regions are translucent, so their alphas do not stack. Menus use `backdrop-filter` inside the page.

### Varying opacity

Each part has its own opacity, and the defaults keep the structure readable: title bar and menu bar 82 %, tabs and toolbar 90 %, sidebar 94 %, file area 98 %; menus close to solid. The part's opacity is drawn as set, or lifted to the contrast floor when the text would be unreadable. Settings → Transparency has a live preview of the window and of a context menu, each using the same region rules as the app.

## Window frame and shadows

Waypoint draws its own title bar, so its windows are frameless (`decorations: false`) and transparent, and the frame rounds its own corners.

| Platform                     | Shadow                                                                                               | Corners                                                                                  | Notes                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux (GNOME, KDE, Cinnamon) | CSS `box-shadow` inside a 8px transparent margin (`--wp-window-shadow`, `--wp-window-shadow-margin`) | CSS `--wp-window-radius` (12 px)                                                         | GNOME paints no shadow for a frameless window, and Tauri's `shadow` option is unsupported on Linux. The resize border sits in the margin: tao's hit area is a fixed 5px strip at the window's outer edge, so the margin is kept small (8px) to keep the grab zone close to the visible edge, and the shadow is sized to fit inside it. |
| Windows 10 and 11            | The OS (`shadow: true`; DWM)                                                                         | Windows 11 rounds them natively and the CSS radius is 0; Windows 10 keeps the CSS radius | Two mismatched radii would clip against each other, so only one rounds. Windows 11 is detected by build number (22000 and up) because it reports the same `10.0.x` version as Windows 10.                                                                                                                                              |
| macOS (not a target)         | The OS (`shadow: true`)                                                                              | CSS radius                                                                               | Follows the alpha shape of the transparent window. Transparency needs Tauri's `macos-private-api`, which rules out the Mac App Store. Untested.                                                                                                                                                                                        |
| Plain browser (development)  | None                                                                                                 | CSS radius                                                                               | No platform is set, so no margin or shadow is drawn.                                                                                                                                                                                                                                                                                   |

On Linux the shadow is removed while the window is unfocused (`--wp-window-shadow-unfocused`, the hairline ring only), which makes the active window stand out when moving between windows. A maximised window has no margin, shadow, rounding or border on every platform. `data-platform` on the root element comes from `@tauri-apps/plugin-os`; the per-platform tokens live in `apps/waypoint/src/theme/tokens.css`. The `window-effects` plugin's `set_shadow_inset` calls `gdk_window_set_shadow_width` with the 8 px margin on every framed window (and zero while it is maximised or full screen), so the compositor leaves the margin out of the window's geometry and a tiled window should sit flush: `src-tauri/src/effects.rs` sets it when a window's page starts loading and after every resize. It is unavailable, with a reason, where the window is not a GTK one. **Status:** the call is made and succeeds on GNOME-style Wayland (a headless Weston, with no tiling to try), and a maximised window is flush; whether a half-tiled window now sits flush on GNOME, KDE and X11 has not been looked at, so the previous limitation stands until it has (see `milestone-5-spikes.md`).
